# Защита Flight Booking

Сценарий рассчитан на 15–20 минут. Перед демонстрацией выполните make up в отдельном Compose-проекте и подготовьте результаты полного make e2e. Финальный прогон F422184A70 от 4 ноября 2026 года: 15/15 PASS за 71,679s, Allure HTML сформирован. Подробности и ограничения проверки записаны в [QA](qa.md).

## 0–3 минуты: что изменилось после прошлых работ

«В ДЗ-1 я проектировал маркетплейс с сервисами Users, Catalog, Feed, Orders, Payments и Notifications, отдельными БД, HTTP и Kafka. В ДЗ-2 реализовал Go HTTP-монолит с общей PostgreSQL. Здесь я сохраняю смысл границ: Booking владеет покупкой и её ценой, Flight — предложением и местами. Предметная область меняется на авиабилеты, а межсервисный контракт — на gRPC по условию задания».

Откройте [C4 и ER-диаграммы](architecture.md). Покажите два процесса и две PostgreSQL в compose.yaml. Новый проект собирается самостоятельно.

«Главное последствие разделения БД: общей транзакции больше нет. Каждый сервис атомарен локально, а между ними возможен временный разрыв состояния. Для восстановления Booking хранит намерение в PostgreSQL до удалённого изменения».

## 3–7 минут: обычное бронирование

Выполните [полный curl-пример](../README.md) от поиска до повторной отмены. На чистых демоданных ожидаются цена места 150050 копеек, итог за два места 300100, остаток 98 после создания и 100 после отмены.

Во время ответа покажите proto/flight/v1/flight.proto: бизнес-операции, Timestamp, enum и описанные коды ошибок. Затем покажите generated-клиент и вызовы GetFlight, ReserveSeats и ReleaseReservation из Booking.

«Idempotency-Key необязателен для совместимости с простым клиентом. Но для повтора после сетевой ошибки клиент задаёт UUID заранее. Один ключ и тот же payload возвращают прежний результат; другой payload даёт конфликт. Без ключа повтор — новая операция».

SQL для проверки обеих сторон:

```bash
docker compose exec booking-db psql -U booking -d booking -c \
  'SELECT id,flight_id,seat_count,total_price,status FROM bookings ORDER BY created_at DESC LIMIT 5'
docker compose exec booking-db psql -U booking -d booking -c \
  'SELECT booking_id,kind,state,error_code FROM booking_operations ORDER BY created_at DESC LIMIT 10'
docker compose exec flight-db psql -U flight -d flight -c \
  'SELECT flight_number,available_seats,total_seats,price,status FROM flights ORDER BY flight_number'
docker compose exec flight-db psql -U flight -d flight -c \
  'SELECT booking_id,flight_id,seat_count,status FROM seat_reservations LIMIT 10'
```

## 7–10 минут: конкуренция, цена и кеш

В отчёте откройте Last seat has exactly one concurrent winner. На одно место приходят 12 параллельных вызовов; результат — один успешный резерв, один ACTIVE в SQL и нулевой остаток. Покажите SELECT FOR UPDATE и общую транзакцию уменьшения остатка с созданием резерва.

Повторите GetFlight и SearchFlights, затем выполните UpdateFlight из README: цена передаётся в копейках, статус — enum. Существующая бронь сохраняет прежнюю стоимость. CANCELLED-рейс исчезает из поиска и не принимает новые резервы; отмена самого рейса не запускает отмену существующих booking.

«Необязательный кеш получает до 50ms на GET и до 50ms на SET, чтобы оставить время на PostgreSQL fallback. Кеш имеет TTL 300 секунд. Перед Redis я читаю маленькую запись revision из PostgreSQL. Мутация меняет данные и revision одним COMMIT. Новые чтения обращаются к новой версии ключей, старые ключи доживают до TTL. Поэтому потерянный ответ COMMIT или недоступный Redis не оставляет старую версию доступной новым чтениям».

Покажите cache hit/miss в логах и TTL из сценария Price snapshot and cache invalidation. Назовите компромисс: PostgreSQL нужен даже на cache hit; это отступление от буквального cache-first в условии ради инвалидации при недоступном Redis.

## 10–15 минут: сбои и восстановление

Покажите Allure-прогон F422184A70; полный fault-набор может занять больше времени, чем сама защита. Если запускаете live, используйте только отдельный Compose-проект: тесты останавливают его контейнеры.

1. Redis outage falls back to PostgreSQL: оба Redis недоступны, поиск и бронирование продолжаются через БД. Sentinel promotes replica and cache recovers: остановлен текущий master, реплика стала master, приложение заполнило кеш на новом узле.
2. Flight outage opens and recovers circuit: не больше трёх вызовов invoker из interceptor, затем OPEN с быстрым 503. Чтение своей брони и списка при этом работает. После паузы один логический HALF_OPEN probe закрывает цепь. Transparent retry gRPC для необработанного сервером запроса остаётся возможным; абсолютный лимит сетевых передач не заявляется. Покажите переходы в логах.
3. Booking crash after reserve is compensated: намерение и удалённый резерв уже записаны, Booking убит до локальной финализации. После старта recovery освобождает места; CREATE становится FAILED, booking отсутствует.
4. Booking crash after release finishes cancellation: места возвращены, Booking убит до смены своего статуса. После старта повторный Release безопасен, CANCEL становится DONE, booking — CANCELLED.

«Компенсация может сама упасть. Тогда намерение остаётся в PostgreSQL и повторяется позже. Для позднего Reserve после компенсации Flight хранит tombstone по booking_id: Release отсутствующей резервации тоже запрещает последующий Reserve. Оба метода берут одинаковый advisory lock».

«Это eventual consistency. Между возвратом мест и завершением отмены клиент может увидеть CONFIRMED. Прогресс требует, чтобы сервисы и PostgreSQL снова стали доступны. Я не обещаю мгновенную распределённую атомарность».

## 15–20 минут: вопросы

| Вопрос | Короткий ответ |
|---|---|
| Почему не одна БД и не общая транзакция? | Задание требует отдельную БД на сервис. Общая транзакция ДЗ-2 больше не пересекает границы владения. |
| Почему gRPC? | Это требование ДЗ-3; контракт типизирован, Go-клиент и сервер сгенерированы из proto. |
| Почему нет FK на booking_id во Flight? | Это другая БД; связь проверяется протоколом. Временный резерв может предшествовать записи booking. |
| Где 3NF? | Авиакомпания отделена от рейса; резерв зависит от booking_id. Имена аэропортов не храним, IATA-коды атомарны. |
| Зачем int64 вместо decimal из ДЗ-2? | Вход — целые копейки RUB, расчёт — точное умножение на целое число мест с проверкой переполнения. Скидок здесь нет. |
| Какую цену фиксирует бронь при одновременном UpdateFlight? | Цену, полученную GetFlight перед ReserveSeats. Это снимок предложения, не текущая цена на момент финального COMMIT. |
| Что защищает от позднего SET старой цены? | Ключ выбирается до чтения payload и сохраняется до SET. Два теста LateFill физически записывают старый payload после мутации и проверяют свежий следующий Get/Search; mutant с повторным выбором revision падает. |
| HTTP_TIMEOUT — это строгие 8 секунд на весь ответ? | Нет. Он ограничивает контекст обработки и чтение запроса. Синхронная компенсация получает отдельный background-бюджет и может продлить ответ; неполное тело сервер ограничивает ReadTimeout. |
| Что если ответ COMMIT потерян? | Исход неизвестен. CREATE возвращает 503 UNKNOWN_OUTCOME; повтор с тем же ключом читает durable journal. DONE возвращает бронь, оставшийся PENDING позже компенсируется. |
| Проверена ли именно потеря ответа COMMIT? | Драйверный fault выполняет настоящий PostgreSQL COMMIT и возвращает ErrBadConn. Booking сохраняет CONFIRMED без Release, повтор Flight не списывает места второй раз. Реальный обрыв TCP в этот момент отдельно не воспроизводился. |
| Можно ли забыть tombstone через пять минут? | Сейчас нет TTL. Иначе очень поздний Reserve снова занял бы места; нужна отдельная политика допустимого срока повторов. |
| Почему Release отсутствующего резерва успешен? | Он сохраняет запрет будущего Reserve и делает повтор компенсации безопасным. |
| Что значит EXPIRED? | Статус предусмотрен контрактом задания. Автоматического истечения нет: срок удержания мест не задан. |
| Sentinel гарантирует сохранность данных? | Нет. Redis реплицируется асинхронно; кеш можно потерять. Источник истины — PostgreSQL. |
| Прочитает ли приложение кеш при отказе PostgreSQL? | Нет: revision читается из БД до Redis. Кеш снимает часть работы с payload, не заменяет БД. |
| Считаются ли три retry тремя ошибками breaker? | Нет, считается один итог логического RPC. HALF_OPEN делает один вызов invoker без retry приложения. Transparent retry gRPC может повторить ещё не обработанный сервером запрос. |
| Бизнес-ошибка открывает breaker? | Нет. NOT_FOUND и RESOURCE_EXHAUSTED подтверждают связь и сбрасывают счётчик последовательных инфраструктурных ошибок. |
| Где аналогия с Avito? | Документация service-item описывает защиту исходящего HTTP-клиента circuit breaker. Я перенёс принцип в gRPC interceptor; продакшен-протоколы и пороги Avito не утверждаю. |
| Можно ли назвать систему полностью отказоустойчивой? | Sentinel покрывает Redis; журнал покрывает перезапуск Booking. PostgreSQL и приложения здесь не реплицированы. |
| Фильтр user_id защищает чужие брони? | Нет. REST не аутентифицирует пользователя; это учебная фильтрация. Авторизации нет. |
