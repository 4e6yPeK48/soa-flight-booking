# ДЗ‑3: Flight Booking на Go — все 10 пунктов

## Архитектура и результат

Создать отдельный репозиторий /Users/mmchupryna/projects/soa-flight-booking: один Go-модуль, два приложения, две PostgreSQL и Redis Sentinel.

Сохранить основу ДЗ‑1: Booking отвечает за оформление, Flight — за рейсы и доступность; каждый сервис изменяет только собственные данные. Объяснить соответствие Orders → Booking и Catalog → Flight. Внутренний HTTP заменить на gRPC по ТЗ. Общую транзакцию ДЗ‑2 заменить локальными транзакциями и восстановлением операций между сервисами.

Стек: Go 1.26, net/http, pgx, protobuf/gRPC, Flyway, PostgreSQL 17, go-redis/v9. Генераторы и зависимости закрепить. Код группировать по доменам, следуя простому стилю ДЗ‑2.

Одна команда docker compose up собирает приложения, генерирует код, применяет миграции и загружает демонстрационные рейсы. REST публикуется на localhost:8081, gRPC — на localhost:50051; базы и Redis доступны внутри сети Compose.

## Контракты и данные

Booking предоставляет все шесть REST-операций:
GET /flights — Поиск по маршруту и необязательной дате.
GET /flights/{id} — Информация о рейсе.
POST /bookings — Создание бронирования.
GET /bookings/{id} — Получение бронирования.
POST /bookings/{id}/cancel — Отмена.
GET /bookings?user_id=X — Бронирования пользователя.

Описать OpenAPI, генерировать DTO и проверять входные данные. Idempotency-Key с UUID необязателен: сервер создаёт ключ при отсутствии. Повтор того же запроса с сохранённым ключом возвращает прежний результат; другой запрос с тем же ключом получает 409.

Flight предоставляет пять RPC: SearchFlights, GetFlight, ReserveSeats, ReleaseReservation и согласованный UpdateFlight. Последний меняет цену и/или статус; пустое изменение отклоняется. Изменение цены сохраняет прежнюю стоимость существующих бронирований. Изменение статуса рейса не запускает автоматическую отмену бронирований.

Принять следующие форматы и ограничения:
- Рейсы, бронирования и операции имеют UUID; user_id — положительный int64.
- Цена и total_price — целые копейки RUB с проверкой переполнения. В документации объяснить отличие от decimal в ДЗ‑2.
- Время передаётся через Timestamp, статусы — через enum. Поиск по дате и ограничение номера рейса за календарный день используют UTC.
- Flight хранит авиакомпании, рейсы, резервации, отметки отмены и версию кэша. Booking хранит бронирования и журнал операций CREATE/CANCEL.
- ER-диаграммы показывают 3NF и ограничения: положительные цена, вместимость и число мест; доступный остаток от нуля до вместимости; прилёт позже вылета; разные аэропорты; UNIQUE для номера рейса с датой и booking_id резервации.
- Между БД нет внешних ключей. Данные пассажира относятся к конкретному бронированию.

Ошибки REST: 400 для неверного ввода, 404 для отсутствующей сущности, 409 для нехватки мест и конфликтов состояния, 503 для недоступного Flight или открытого breaker, 504 для дедлайна Flight. Ошибка межсервисной аутентификации возвращается как 502. Ответ содержит код и описание ошибки, при наличии — идентификатор операции.

## Транзакции и восстановление

1. Резервирование. Flight сериализует операции по booking_id, затем блокирует рейс через SELECT FOR UPDATE. Изменение остатка и создание резервации выполняются одной транзакцией. Повтор с прежними параметрами успешен; несовпадающие параметры или ранее отменённый резерв дают FAILED_PRECONDITION.
2. Возврат мест. ReleaseReservation возвращает места ровно один раз; повтор для RELEASED возвращает OK. Для отсутствующего резерва сохраняет постоянную отметку отмены и возвращает успех. Это запрещает запоздалому Reserve списать места после компенсации.
3. Создание Booking. Первая короткая транзакция сохраняет и коммитит PENDING до RPC. Затем без транзакции выполняется GetFlight → ReserveSeats. Финальная короткая транзакция блокирует строку журнала, проверяет PENDING и срок, затем атомарно создаёт CONFIRMED и завершает журнал.
4. Компенсация. Фоновая обработка раз в секунду выбирает требующие очистки или просроченные операции через FOR UPDATE SKIP LOCKED и коммитит PENDING → COMPENSATING до RPC Release. Незавершённый CREATE освобождает резерв и только после подтверждённого Release помечается неуспешным. Создание позднее не возобновляется.
5. Неизвестный COMMIT. Восстановление сначала перечитывает журнал под блокировкой. Подтверждённое бронирование сохраняется. Клиент получает ошибку с обозначением неизвестного результата и повторяет исходный Idempotency-Key для получения итога.
6. Отмена Booking. Намерение CANCEL сохраняется до ReleaseReservation. После успеха записываются CANCELLED и завершение операции. При перезапуске обработка повторяет идемпотентный Release и завершает отмену.

## Кэш и устойчивость

Все пять RPC защищены server interceptor: API key передаётся в metadata, значение берётся из env. Отсутствующий или неверный ключ даёт UNAUTHENTICATED.

Retry и circuit breaker размещаются в клиентском interceptor Booking:
- Всего три попытки, паузы 100/200 мс; повторы только для UNAVAILABLE и DEADLINE_EXCEEDED.
- Начальные бюджеты: 500 мс на попытку, 2 с на RPC, 8 с на REST; просроченный CREATE доступен восстановлению через 10 с.
- Настроенные retry-политики gRPC отключаются. Лимит — три прикладных вызова interceptor/invoker; безопасные transparent retries до обработки запроса сервером могут выполняться библиотекой grpc-go.
- Breaker считает итог RPC после повторов: пять последовательных инфраструктурных ошибок в окне 60 с открывают цепь на 15 с. Затем допускается один HALF_OPEN-вызов без retry.
- Успешный или бизнес-ответ закрывает цепь; инфраструктурный сбой открывает снова. Переходы логируются, параметры задаются через env. Автомат проверяется с управляемыми часами.

Redis работает как master + replica + три Sentinel с кворумом два. Клиент использует NewFailoverClient; выбор трёх Sentinel объяснить через возможность пережить отказ одного участника.

Для GetFlight и SearchFlights реализовать cache-aside, TTL 300 секунд и логи hit/miss. Версия и UUID пространства кэша хранятся в PostgreSQL; новая БД получает новый UUID. Мутации атомарно меняют данные и версию.

Чтение сначала получает версию, затем обращается к Redis. Старые версии становятся недоступны и исчезают по TTL. Это закрывает гонку заполнения кэша и возврат старых значений после переключения Redis. При ошибке Redis выполняется чтение PostgreSQL. Компромисс: каждое обращение к кэшу сохраняет короткий запрос версии в PostgreSQL.

## Проверки, документация и приёмка

Проверять поведение каждого блока до перехода к следующему:
- Все REST/RPC-операции, аутентификацию каждого RPC, валидацию, границы денежных значений и ограничения БД.
- Конкурентное резервирование последнего места: ровно один успех, отсутствие отрицательного остатка.
- Повторы Reserve/Release, конфликт параметров, потерю ответа после успешного Reserve и запоздалый Reserve после компенсации.
- Перезапуск Booking после резервирования; восстановление отмены после успешного Release; неизвестный результат COMMIT.
- Cache hit/miss, TTL, инвалидацию после Reserve, Release и UpdateFlight, гонку заполнения, недоступность Redis и переключение master.
- Сохранение цены существующего Booking после UpdateFlight; исключение отменённого рейса из поиска и запрет новых резервов.
- Число попыток retry, отсутствие повторов бизнес-ошибок, переходы breaker и немедленный 503 в OPEN. Чтение собственных бронирований работает при недоступном Flight.

Использовать Go unit/integration/E2E, реальные PostgreSQL, SQL-проверки инвариантов, race detector и vet. Allure сохраняет результаты, очищенные HTTP/gRPC-вложения и логи; CI публикует отчёт. Сценарии отказов выполняются последовательно в отдельном Compose-проекте.

Подготовить README с curl/grpcurl, OpenAPI и proto, C4, ER, последовательности создания и восстановления, соответствие пунктов 1–10 проверкам и материал для защиты. Каждый отход от ДЗ‑1/ДЗ‑2 объяснить причиной и ценой решения. На примере service-item показать размещение breaker в исходящем клиенте; эксплуатационные пороги выбрать для учебного стенда.

Приёмка: чистый запуск Compose, повторный запуск с сохранёнными данными, успешные make check и make e2e, проверяемое подтверждение каждого пункта задания.

Начальная конфигурация — один экземпляр каждого приложения. EXPIRED остаётся предусмотренным статусом; автоматическое истечение резерва ТЗ не задаёт.

Восстановление завершится после возврата зависимостей; до этого возможен временный резерв.
